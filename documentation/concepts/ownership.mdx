**Building the client is the ownership check.** `ArcaneClient::init` runs it once at launch with your title's game id; you do not add a second ownership step.

Init prefers a local ticket cache. When the ticket is missing or expired, it contacts the Arcane desktop app on loopback (`127.0.0.1:39284`) to refresh online — and may open Arcane via the `arcane-powered://` deep link if the app is not running.

## Game id

The string you pass to `init` is the **game id** of your title in the Arcane portal. It keys the local flag and ticket files, names the title in every desktop route, and must match the ticket's `gid` claim.

It is validated before any I/O: ASCII letters, digits, `_`, `-`, `.`, at most 256 bytes. Anything else is `invalid_game_id`.

It is **not a secret**. The id identifies a title; it proves nothing on its own. What proves ownership is the signed ticket below — an ES256 JWT bound to an account and a device — which nobody can mint from the id.

## Default init policy

`ArcaneClient::init(game_id)`:

1. Validates the game id
2. Reads `flags/{game_id}.json` for `drm_enabled`
3. If `drm_enabled` is `false` → `OwnershipStatus::DrmDisabled` (no ticket required)
4. Otherwise (flag `true` or missing) → runs the offline ownership check
5. If the offline check fails with `ticket_missing` or `ticket_expired`:
   - Probes the desktop health endpoint
   - Opens `arcane-powered://sdk/ownership?game_id=…` when Arcane is not running
   - Calls the desktop's ownership refresh
   - Re-runs the offline check against the refreshed cache
   - If the desktop reported DRM is off for this title and no ticket appeared, resolves to `DrmDisabled` rather than failing

Everything learned along the way — `user_id`, ticket expiry — is kept on the client, alongside the `game_id` init was given. See [Client](/concepts/client).

## Offline check (what init runs when DRM is on)

1. Resolves the ticket for the **signed-in account** (see below)
2. Rejects clock rollback vs `last_seen_wall_time`
3. If `drm_enabled` on the ticket file is false → `DrmDisabled`
4. Ensures the ticket string is non-empty
5. Compares the cached `device_hash` to the local fingerprint
6. Verifies the JWT (ES256, issuer `arcane-drm`, audience `arcane-game-sdk`)

## Which account's ticket

`session.json` — written by the Arcane desktop app on sign-in and sign-out — is the offline source of truth for who is signed in.

| `session.json` | Result |
|---|---|
| Names a user | Reads exactly `tickets/{user_id}/{game_id}.ticket`. No fallback. |
| Records a signed-out state | `not_authenticated` |
| Absent (older Arcane desktop) | Scans ticket directories: one match is used, several give `ambiguous_session` |

The no-fallback rule matters on shared machines. A ticket belonging to a different account is correctly signed and correctly bound to the device, so nothing else would reject it — only the account check does.

## Desktop refresh errors

When init must refresh online, the desktop (and cloud) can return distinct failures:

| Desktop / cloud | SDK code | Meaning |
|-----------------|----------|---------|
| `not_owned` | `not_owned` | Account does not own the title |
| `offline` / cloud unreachable | `network_required` | Need internet once to mint a ticket |
| `not_authenticated` | `not_authenticated` | Arcane is open but the user is signed out |
| Loopback never comes up | `arcane_unavailable` | Could not open or reach Arcane |

An unrecognised desktop error code becomes `ticket_invalid` with the original string preserved in the error's `context.desktop_error`, so a newer launcher never produces a silent failure. See [Errors](/concepts/errors) for the full table.

## Data layout

```
{app_data}/Arcane Powered/drm/
├── machine_id
├── jwks.json
├── session.json
├── flags/{game_id}.json
└── tickets/{user_id}/{game_id}.ticket
```

`{app_data}` is the OS application data directory (the SDK resolves this internally).

## Ticket claims

| Claim | Role |
|-------|------|
| `gid` | Must match the game id you passed to init |
| `own` | Must be `true` |
| `dev` | Must match local `device_hash` |
| `iat` / `nbf` / `exp` | Time bounds (±5 min skew) |
| `sub` / `jti` / `ver` | Subject, ticket id, version |

## Device fingerprint

`machine_id` is a UUID written once under the DRM root (mode `0600` on Unix). `device_hash` is the first 16 bytes of SHA-256(`machine_id`), hex-encoded, and is readable from the client as `device_hash()`. Tickets are bound to that hash so they cannot be copied to another machine.

## JWKS

Verification keys come from `jwks.json`. The JWT `kid` selects the key when present. If JWKS is missing or the `kid` is unknown, the SDK returns `ticket_invalid` naming the resolved path — refresh via the desktop app.

## What ownership does not prove

The SDK verifies that *this machine, for this account, holds a valid signed entitlement for this title*. It does not — and cannot — prove that the process making the call is genuinely your game. Any secret compiled into a game binary is extractable, and the init call itself can be patched out. That is also why the game id is not treated as a secret: hiding it would buy nothing. Treat ownership as a platform integration, not as anti-tamper; enforcement that must hold against a determined attacker belongs on the server.
